Refactored deployment and prototype-validation plan

Status and safety boundary

The parallel rewrite is a desk-verified future implementation until the recorded physical-validation sequence in this document has been completed on the GrowTech Wall prototype. Source review, laptop tests, simulation, and firmware compilation do not establish physical behavior.

This document is a future deployment procedure. No Raspberry Pi configuration, udev rule, service, camera, serial device, Arduino, relay, pump, motor, or arm controller was accessed or changed while preparing the rewrite.

The legacy application and firmware remain the rollback baseline:

• Raspberry Pi/GUI/GTW_GUIv2.py and Raspberry Pi/GUI/ServoControl.py;

• gantry_main/;

• NFT_Hydroponics/NFT_Hydroponics_main_copy_20250609193150/;

• the existing model, calibration, and Arm Action File/ assets.

Do not begin physical validation without an authorized operator, an agreed safe-state procedure, a clear work area, actuator and chemical isolation appropriate to the step, and a second person able to remove power. The GUI Stop control is orchestration cancellation; it is not a verified emergency stop.

Pre-deployment evidence gate

Record all of the following before changing the prototype:

• Repository commit, branch, and worktree status.

• Raspberry Pi identity, SD-card identity and layout, OS/Python versions, and the active virtual-environment freeze.

• The SHA-256 of Raspberry Pi/GUI/bestv5.pt and the refactored source tree.

• readlink -f and udevadm info evidence for the intended Gantry and Hydroponics Nano devices, with actuator power isolated.

• Existing Gantry and Hydroponics firmware source/hash, Arduino board FQBN, bootloader/processor option, port identity, compiler version, library versions, and successful rollback method.

• Controller wiring, power domains, installed endstop polarity, relay/load isolation, safe substitute-fluid arrangement, and operator-approved stop/recovery method.

• Robotic-arm controller identity, native-UART configuration, deployed action-group mapping, clearance envelope, fixtures, and power-removal procedure.

Items 5 through 7 are not fully present in the repository today. Missing evidence is a blocking validation gap, not permission to guess a board setting, wire, calibration, or arm action.

Exact Arduino compile and upload order

No Arduino toolchain or verified build metadata was available during desk implementation. Do not install tooling or select a convenient board profile as a substitute for the deployed metadata.

After the pre-deployment gate is complete, use this fixed order and change only one controller at a time:

• Capture both controllers first. Save the current Gantry and Hydroponics source/flashed-artifact hashes when available, board settings, library versions, and a tested rollback command. Disconnect or isolate actuator/load power as required by the approved procedure.

• Compile the Gantry rewrite first. Compile gantry_main_refactored/gantry_main_refactored.ino with the captured legacy Gantry board FQBN, processor/bootloader, compiler, and AccelStepper version. Do not upload if compilation differs unexpectedly or rollback is unavailable.

• Upload only the Gantry Nano. Confirm the port by device metadata, keep the Hydroponics Nano unchanged, upload, then perform the Gantry-only startup, homing, endstop, 24-position, timeout, and recovery checks below.

• Gate or roll back. If any Gantry result differs from the approved legacy expectation, stop, restore gantry_main/gantry_main.ino with its matching modules using the captured toolchain, and close the discrepancy before continuing.

• Compile the Hydroponics rewrite second. Compile NFT_Hydroponics_refactored/NFT_Hydroponics_refactored.ino with the captured legacy Hydroponics board FQBN, processor/bootloader, compiler, Wire, and RTClib versions.

• Upload only the Hydroponics Nano. Confirm the port by metadata, keep chemical loads disconnected or routed to the approved substitute-fluid setup, upload, then perform status, sensor, relay, timing, and recovery checks below.

• Gate or roll back. If any Hydroponics result differs, restore the timestamped legacy sketch with the captured toolchain before integrated testing.

• Do not upload robotic-arm action files in this sequence. The .rob loading procedure and exact deployed mapping remain unverified. Arm validation uses the already-deployed controller image only after its identity and group mapping are recorded.

“Gantry first, Hydroponics second” is the upload order. It does not resolve the missing board/toolchain metadata, and it is not authorization to upload.

Physical prototype validation record

For every step, record date/time, operator and observer, Git commit, Pi/SD identity, controller identity, firmware hash, wiring/power state, expected result, observed result, logs or photographs, pass/fail, and rollback taken. A later document may use hardware-validated future work only for results supported by this record.

1. Serial aliases and native UART

With actuator and chemical-load power isolated, inspect without transmitting commands:

readlink -f /dev/arduino_gantry
readlink -f /dev/arduino_hydroponic
test -e /dev/arduino_roboticarm && echo present || echo absent
ls -l /dev/ttyAMA1

The legacy deployment evidence expects Gantry to resolve to /dev/ttyUSB1, Hydroponics to /dev/ttyUSB0, /dev/arduino_roboticarm to be absent, and the arm to use native /dev/ttyAMA1. The USB aliases are physical-topology mappings, not board-serial-number identities. Confirm device metadata; do not identify a controller by tty number alone.

2. Pi GUI startup and connection lifecycle

• Start python app.py --simulate; verify the Dashboard, Gantry & Arm, Hydroponic, and Vision tabs and close it cleanly.

• Establish the approved physical safe state and start python app.py once.

• Record camera/model/controller connection messages and confirm the GUI remains responsive.

• Close the GUI and verify workers and opened transports terminate. Do not infer actuator safe state merely because the process closed.

• Start it a second time to characterize Nano reset/re-home behavior and confirm there is no port-lock leak.

3. Camera and YOLO

• With controller movement inhibited, confirm camera index 0 is the intended USB camera and produces the expected 640 by 640 request.

• Capture approved reference scenes for No detection, Immatured, Matured, and each deployed disease label.

• Verify confidence threshold 0.3, selection of the single highest-confidence detection whose center lies from w/6 through 5w/6, displayed label, annotation, and saved path ~/plant_images/<plant>/<YYYYmmdd_HHMMSS>.png.

• Compare results with the legacy application on the same saved frames. Record discrepancies; a matching model hash alone is insufficient.

4. Gantry startup, homing, and all 24 positions

• Clear the motion envelope and establish the approved power-removal method.

• Observe startup homing without issuing a movement command. Record endstop order, direction, dual-Y behavior, debounce/bump behavior, serial transcript, zero position, and completion.

• Validate 0 0 re-home and explicitly record that the deployed legacy protocol completes with Homing complete. and does not emit POS for this command. Confirm the refactor advances on that line rather than waiting indefinitely. If a controller variant emits the legacy-expected fresh POS 1 1, record and validate that alternate accepted path separately.

• Visit positions in the preserved snake order: 1,2,3,4,5,6,12,11,10,9,8,7,13,14,15,16,17,18,24,23,22,21,20,19.

• At each position, compare START x y, POS x y, physical alignment, direction, dual-Y squareness, and measured stop position with the legacy baseline.

• Separately validate U, D, L, R, G, P, X during patrol, O, disabled-command re-enable/re-home behavior, and the 60-second inactivity home-and-disable behavior. Treat O as legacy home-Y-then-disable behavior, not an emergency stop.

6. Hydroponics status and sensors

• Keep all pump/relay loads isolated. Capture startup output, RTC-present behavior, lost-power behavior, initial output levels, and the two 200 ms light-relay blinks.

• Verify one complete STAT,<ms>,<water>,<ec>,<ph>,<light>,<water>,<acid>,<fert>,<pest> line per approximately 1000 ms and verify fragmented/combined input is displayed correctly by the Pi.

• Compare raw readings and converted water, EC, and pH values with the legacy firmware under the same calibrated references. Do not approve accuracy without known solutions, calibration history, and sensor-condition records.

7. Individual water, light, and dosing outputs

Using electrically isolated indicators or the approved substitute-fluid setup, test only one output at a time:

• WATER_PUMP:ON, then WATER_PUMP:OFF; confirm installed relay polarity and status.

• LIGHT:ON, then LIGHT:OFF; confirm manual override and restoration through a valid light-hour command.

• DOSE:ACID:<mL>; measure output duration and delivered substitute-fluid volume.

• DOSE:FERT:<mL>; verify Fertilizer A and B activate and stop together, then measure both flows separately.

• DOSE:PEST:<mL>; verify the preserved legacy limitation that the supplied mL does not set pesticide duration and that the current global doseTimeMs is used.

• Validate TARGET_EC, TARGET_PH, DOSE_TIME, LIGHT_ON_HOUR, and LIGHT_OFF_HOUR with controlled values and no production chemicals.

• Validate the ten-minute per-channel automatic EC and pH dose spacing with recorded simulated/reference sensor conditions. Do not shorten timing constants in a build claimed to be behavior preserving.

8. Automation dry run

• Run Scan Only first with arm and chemical outputs isolated. Verify all 24 Gantry moves, captures, labels, image saves, cancellation boundaries, and completion state.

• Resolve and document the home-completion behavior before Full Auto. The legacy 0 0/POS mismatch is an explicitly documented bug; the refactored state transition must be compared against the accepted validation expectation.

• Run Full Auto using inert props and substitute fluids only. For each label class, verify the preserved dispatch: no detection/immature to group 5; mature to harvest groups 1 and 2 followed by transplant groups 3 and 4 and group 5; other/disease to DOSE:PEST:11, group 6, then group 5.

• Record Gantry/arm coordination at column 1, where harvest temporarily moves to column 2 for storage before returning.

9. Stop, failure, and recovery

Test cancellation at safe boundaries during scan, the 100-ms slices of the scan-only post-capture interval, Gantry wait, arm wait, capture, and hydroponics interaction. Confirm the GUI remains responsive and reports failure without Tk access from a worker. Then characterize controller disconnect/reconnect and application restart with loads isolated.

With actuator and dosing outputs isolated, validate each Phase 2C endpoint policy: startup failures leave the endpoint visibly offline; Gantry/Hydroponics/camera/model failures stop the affected operation and show an actionable error; an unavailable arm shows the legacy-compatible skip warning and the containing workflow continues; a failed pesticide dose stops before arm group 6; and no path silently retries or selects an alternate endpoint. Decide explicitly whether the arm skip-and-continue policy is acceptable before approving real workflows.

The acceptance record must state that GUI Stop cannot interrupt a blocking Nano move or an already-running arm group unless a separately approved, hardware-validated safety change has been implemented. Do not describe closing the GUI, O, serial disconnect, or a software timeout as an emergency stop.

Rollback procedure

• Stop the refactored application and remove actuator/load power using the approved physical procedure. Verify ports/processes are closed; independently establish hardware safe state.

• If only Pi software changed, reactivate the untouched legacy environment and manual entry point:

``bash cd "/home/growtechwall/Desktop/IDP-Grow-Tech-Wall/Raspberry Pi/GUI" source /home/growtechwall/venv-ultralytics/bin/activate python3 GTW_GUIv2.py

Start it only after the same physical preflight because legacy import opens the camera, native arm UART, and Nano ports.

• If Gantry firmware changed, restore gantry_main/gantry_main.ino plus its matching GantryController.h/.cpp first, using the captured legacy FQBN/toolchain/library versions. Re-run the Gantry-only baseline checks before proceeding.

• If Hydroponics firmware changed, restore NFT_Hydroponics/NFT_Hydroponics_main_copy_20250609193150/NFT_Hydroponics_main_copy_20250609193150.ino second, using its captured legacy build metadata. Re-run output-isolated status checks.

• Do not alter or reload arm action files as a rollback shortcut until their controller-specific deployment mapping is verified.

• If repository or environment recovery is required, restore the approved commit and, when necessary, the private SD-card image. Keep disk images and credentials outside Git.

• Record the reason for rollback, exact artifacts restored, observed result, and any remaining unsafe or unknown state.

Rollback restores the known legacy software artifacts; it does not by itself prove wiring, calibration, arm pose, fluid state, or mechanical safety.
